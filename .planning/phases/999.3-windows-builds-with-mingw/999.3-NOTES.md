# 999.3 Windows builds with the GNU toolchain (MinGW) — notes

Captured 2026-10-08 while splitting the Windows CI job. Johannes asked why `windows-mingw-platform` is so fast (about 2 minutes against two hours for MSVC) and whether MinGW would bring any benefit. Decision: not now; backlog for the installer milestone.

## Why the MinGW job is fast today
It never builds the engine. It runs only the platform tests, the editor core and kit tiers, the Resource Editor core tier (plain Zig against a fake bridge), the overlay spike build and the GPU probe, from a checkout without `Data/`. `build.zig` (resource core tier comment) says the engine C++ does not build on `x86_64-windows-gnu`.

## First blocker
`Sources/src/Platform/LegacyVariant.h` includes MSVC's `comutil.h` on any `_WIN32` target, and MinGW does not ship it. The header is included by the `StdAfx.h` of nearly every engine module (Main, Common, AILogic, Scene, SFX, UI, Formats, Game, RandomMapGen, ...), so every module stops there. The header already carries a portable `variant_t`/`bstr_t` for macOS and Linux; switching the condition to `_MSC_VER` would let MinGW take it. Untried: more MSVC-only code (SEH `__try`, MSVC intrinsics, `#pragma comment(lib)`, COM) is likely behind it, so the size of the port is unknown until a build is attempted.

## Benefits
1. Windows packages built with Zig alone, on any host: no Visual Studio lookup, no MSVC or Windows SDK paths. Useful for contributors and for the installer.
2. Release packages cross-compiled on a Linux runner (cheaper and faster to start than Windows). Tests that run the Game still need a Windows runner.
3. The same C++ standard library (libc++) on every platform, removing a class of mac-works-Windows-breaks bugs (the C++14 default, the `variant_t` shim).

## Not a benefit
Performance: both targets compile with Zig's clang/LLVM, so code generation is the same. Only the standard library implementation differs, a small effect either way next to the engine and the GPU.

## Costs
- Debug info is DWARF (gdb/lldb), not PDB: the cdb/WinDbg crash recipe and Visual Studio debugging do not apply.
- A second Windows configuration to keep green, unless it replaces MSVC for packaging only.
- Port size unknown (see First blocker).

## Suggested order
1. Switch `LegacyVariant.h` to `_MSC_VER`, build `install-game -Dtarget=x86_64-windows-gnu`, list the next failures and size the port.
2. If small: make the game build, run the engine tier on Windows with the gnu build, compare against MSVC.
3. Decide whether the installer packages from the gnu build on Linux, and whether MSVC stays for debugging.
