# 999.7: Startup flags and config file - Context

**Gathered:** 2026-10-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Every current setting of the Game and the editors becomes a settable startup flag, and
every flag can also come from a config file, so a player or tester can reproduce a setup
without touching menus.

- Each setting gets a named command-line flag (`--<setting>[=value]`), completing the
  startup flags the binaries already accept (`-windowed`, `-mod=`, `--check`, and so on).
- A config file holds the same settings as `key=value` lines. When a config file is set,
  whatever is in it is applied. Individual flags on the command line take precedence over
  config values (flag wins).
- A flag (or editor menu action) saves all current settings into a config file as a backup,
  so a known-good setup can be captured and replayed.
- The same semantics apply to the Game and to the editors (one shared reader where the
  editor kit's settings file already exists; the Game's profile/options settings map onto
  flags without moving their storage).

Out of scope: changing what the settings do, a new settings UI beyond exposing existing
settings as flags, and cloud-synced settings (the profile seams stay).

## Acceptance shape (for the planner)

- `--save-config <file>` (or the documented editor action) writes every current setting.
- Running with a config file applies its values; a flag for the same setting overrides.
- Unknown config keys and unknown flags fail loudly with the setting's name.
- One test per rule, deterministic, per the house test rules (tracked Data only).
